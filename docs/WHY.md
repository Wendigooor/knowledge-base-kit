# Why Knowledge Base Kit?

## Проблема

Мы — enterprise. SoftSwiss.

Десятки микросервисов на Ruby, Python, TypeScript. Легаси 10+ лет. Сотни разработчиков, системных аналитиков, архитекторов, QA, продактов. Контекст постоянно меняется: новые фичи, багфиксы, миграции, ревью, ретроспективы.

Контекст живёт:
- В головах у людей (уходит когда человек уходит)
- В Confluence (никто не обновляет)
- В Jira (размазан по сотням тикетов)
- В коде (читай 50k строк чтобы понять один эндпоинт)
- В Slack-обсуждениях (потерян навсегда)

**LLM не могут работать с этим контекстом.** Они видят только то что влезло в промпт. А промпт — это 8k, 32k, 128k токенов. А контекста — миллионы токенов.

**Люди не могут работать с этим контекстом.** Системный аналитик тратит 2 дня чтобы понять как работает один сервис. Архитектор — неделю чтобы собрать ADR. Новый разработчик — месяц чтобы въехать.

## Решение

Knowledge Base Kit — это **база знаний, которая живёт и дышит вместе с проектом**.

Не вики. Не Confluence. Не README.md.

Это структурированное хранилище фактов о системе:
- Архитектурные решения и их обоснования
- Контракты между сервисами
- Схемы данных, миграции, инварианты
- Принятые решения (ADR) и отклонённые альтернативы
- Runbooks, метрики, дашборды
- Опыт эксплуатации: что ломалось, как чинили
- Зависимости и их версии
- Роли команды и зоны ответственности

**Ключевые требования:**

1. **Читаемо людям** — не просто вектора для LLM. Markdown с заголовками, ссылками, диаграммами.
2. **Обновляемо LLM** — агенты могут добавлять и обновлять записи. Автоматически, по крону, без человека.
3. **Версионировано** — каждое изменение сохраняется. Можно откатиться на любую версию.
4. **Ищется семантически** — "найди все решения связанные с миграцией PostgreSQL" — LLM находит по смыслу, не по ключевым словам.
5. **Синхронизируется** — между инстансами, между средами, между командами.
6. **Проверяемо** — QA может пройти по ссылкам и подтвердить что документация соответствует коду.

## Как это отличается от существующих решений

| Продукт | Хранилище | Версионирование | Semantic search | Auto-update |
|---------|-----------|-----------------|-----------------|-------------|
| Confluence | Pages | ❌ Нет | ❌ Только full-text | ❌ |
| Notion | Blocks | ⚠️ Частично | ❌ | ❌ |
| Git-based Wiki | Markdown в git | ✅ Git history | ❌ | ❌ |
| Vector DB (Pinecone) | Вектора | ❌ | ✅ | ❌ |
| **KBK** | ChromaDB + Git | ✅ Версии + git | ✅ Semantic | ✅ Auto-sync |

KBK — единственное решение которое покрывает **все 6 требований** сразу.

## Целевая аудитория

| Кто | Как использует KBK |
|-----|-------------------|
| **System Analyst** | Пишет spec → KBK сохраняет → разработчик читает → LLM проверяет контракты |
| **Architect** | ADR → KBK → команда видит → LLM учитывает при code review |
| **Developer** | Читает контекст → пишет код → KBK обновляется |
| **QA** | Проверяет что docs = код → KBK хранит acceptance criteria |
| **Product Manager** | Спрашивает "почему это так?" → KBK отвечает |
| **New hire** | onboarding через KBK — 2 дня вместо месяца |

## Когда НЕ нужно

KBK не нужен если:
- У вас один сервис и 3 разработчика
- У вас нет легаси (всё с нуля)
- Вся документация в README.md и это работает
- Вы не используете LLM в разработке

Если хотя бы одно из этого про вас — KBK overkill. Используйте Obsidian, Notion или просто Confluence.
