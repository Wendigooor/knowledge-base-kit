# Протокол синхронизации

## Цель

Обеспечить консистентность знаний между несколькими инстансами LLM-агентов.

## Модель: Peer-to-Peer Push/Pull

Все инстансы равноправны. Нет центрального сервера. Синхронизация — через общий git-репозиторий.

```
┌────────────┐     push     ┌──────────────┐     pull     ┌────────────┐
│ Hermes A   │─────────────▶│  GitHub Repo  │◀─────────────│ Hermes B   │
│ (M5 Pro)   │◀────────────┘  (knowledge)  └─────────────▶│ (M1 Pro)   │
└────────────┘     pull     └──────────────┘     push     └────────────┘
```

## Поток синхронизации

### Pull (получение изменений)

1. `git pull --rebase origin main` — получить последние изменения
2. `kbk seed` — импортировать JSON-экспорт в локальную ChromaDB
3. Проверить `sync-log.md` на наличие предупреждений о конфликтах

### Push (отправка изменений)

1. `kbk export` — экспортировать ChromaDB в JSON
2. `git add + git commit` — зафиксировать изменения
3. `git push origin main` — отправить в общий репозиторий

### Two-Way Sync (полный цикл)

```bash
# 1. Получить чужие изменения
git pull --rebase origin main

# 2. Импортировать в локальную ChromaDB  
kbk seed

# 3. Экспортировать локальную ChromaDB (с нашими изменениями)
kbk export

# 4. Отправить
git add -A
git commit -m "sync: $(date -u +%Y-%m-%dT%H:%M:%SZ)"
git push origin main
```

## Обнаружение конфликтов

Конфликт возникает когда два инстанса изменили один и тот же документ между синхронизациями.

### Как обнаруживается

1. При `kbk seed` после `git pull` проверяется version документа
2. Если версия в локальной ChromaDB **выше** чем в импортируемом JSON → конфликт
3. Если версия в JSON **выше** чем локальная → принимаем JSON (remote wins)

### Как разрешается

По умолчанию: **кто последний запушил — тот и прав** (last-writer-wins).

Альтернативные стратегии:

| Стратегия | Поведение | Когда использовать |
|-----------|-----------|-------------------|
| `last-writer-wins` | Побеждает документ с более поздним updated_at | По умолчанию |
| `keep-local` | Локальная версия всегда побеждает | Если инстанс — primary |
| `keep-remote` | Remote версия всегда побеждает | При первом seed |
| `manual` | Конфликт логируется, требует вмешательства | Для критичных данных |

```bash
# Разрешить конфликт вручную: посмотреть обе версии
kbk history --collection projects --id "foo"

# Сравнить две версии
kbk diff --collection projects --id "foo" --v1 2 --v2 3
```

## Catch-Up после простоя

Если инстанс был выключен и пропустил несколько циклов синхронизации:

```bash
# Проверить когда был последний пуш
kbk status

# Если overdue > 1 час — запустить catch-up
kbk sync
```

Catch-up скрипт проверяет время последней синхронизации:
- > 3 часов → запустить sync немедленно
- > 24 часов → запустить sync + seed (полная перезагрузка)

## Рекомендации

1. **Частота синхронизации:** каждые 30 минут (через cron)
2. **Не пушить пустые экспорты:** проверять `git diff --quiet` перед commit
3. **Логировать:** `sync-log.md` с таймстемпами и статусом
4. **При конфликте:** не молчать, записать в лог и сообщить
5. **UUID для документов:** использовать стабильные human-readable id, не UUID
